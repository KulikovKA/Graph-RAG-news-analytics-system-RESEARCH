# Stage 3A.5.10.1 · долгоживущий runtime

Гипотеза состоит в том, что повторная загрузка моделей объясняет существенную часть latency исходного pipeline. Проверяем её замерами, отдельно от различий первого и последующих вводов. Baseline — live Stage 3A.5.10, commit `85b69302f6d3c0b4a5d3630b46194f7646ddafda`. Сравнение — последовательная сессия c однократной загрузкой, затем два warm вопроса. Фиксируем также cold запрос новой сессии. Каждая ветвь эксперимента запускается в отдельном Python-процессе, по три вопроса в одинаковом порядке. Обе ветви читают один live Neo4j через Bolt. API-вызовов Groq нет.

Входы, лицензии и границы корпуса действуют по [Stage 3A.5.10](../benchmark_3a5_10/SPEC.md). Берём тексты вопросов A01, B01 и C09 из прежнего smoke. Доступа к Gold, ожидаемым ответам и историческому holdout в измерении нет. [Профиль](../benchmark_3a5_9/PROFILE.json) фиксирует corpus, graph snapshot, версии и SHA моделей, CPU-only, 4 потока, seed 42 и параметры retrieval. Оба режима используют тот же Harmony tokenizer, параметры контекста и prompt. KG, model assets, ranking и замороженные результаты используются для чтения.

| ID | Критерий и проверка |
|---|---|
| R1 | В одной сессии GLiNER и E5 загружаются один раз, повторно используются analyzer, linker и entity cache. Unit и счётчики реальных загрузок, включая ошибку между вопросами. |
| R2 | Neo4j driver закрывается при выходе и исключениях, включая `exit`, EOF и Ctrl+C. Повторный запрос после ошибки использует ту же рабочую сессию. Unit. |
| R3 | Сравнение трёх пар входов даёт идентичные capped seeds, упорядоченные Top-5, source triples, offsets, точные окна и сообщения. Сравнение с baseline и отдельная проверка provenance по корпусу. |
| R4 | Отчёт фиксирует число загрузок, время загрузчиков, cold/warm, retrieval, context, end-to-end без API и OS peak RSS. Публикуются все парные наблюдения и их границы. |
| R5 | `--question` и `--replay` сохраняют поведение. `--interactive` выполняет последовательные turn и освобождает ресурсы при завершении. Unit и запуск CLI. |

## Дизайн и план

Runtime владеет моделями и driver в области одного контекстного менеджера. Рабочие analyzer/linker лениво загружают веса при первом соответствующем обращении. Профиль, версии, исходники и entity cache проверяются при создании сессии. Штатная read-only проверка снимка перед и после каждого retrieval сохраняется. Интерактивная область также владеет tokenizer контекста для одной конфигурации. Выход закрывает driver и освобождает ссылки сессии на модели. Новый процесс начинает с cold start. Одиночный режим создаёт отдельную короткую сессию. Восстановление после сбоя запуска — новая сессия с теми же frozen входами.

Замеры wall-clock в секундах через perf_counter. GLiNER load — вызов AutoExtractor.from_pretrained, отдельно от SHA-проверок, схемы и inference. E5 load — штатный E5Encoder._load, включая tokenizer и собственные проверки хешей. Инструментирование подключается только в программе измерения. Query analysis и linking содержат эти длительности, если загрузка была в запросе. Retrieval latency включает клиентскую проверку снимка, Bolt и retrieval. End-to-end без API — от приёма вопроса до построенного контекста. Для первой строки runtime сюда включается запуск сессии. OS peak RSS — максимум всего процесса к концу вопроса, с предыдущими пиками. Хеши парных артефактов, точные версии и команды сохраняются в отчёте.

Бюджет — один процесс с моделями одновременно, до 10 минут на ветвь и 8 GiB peak RSS. При расхождении профиля, снимка или provenance прекратить оценку ускорения. Критерий ускорения — warm строки быстрее своих baseline-пар при совпавшем результате, без дополнительных загрузок. Случайные колебания дискового кэша, Bolt и первая инициализация библиотек учитываются в интерпретации. Три пары предназначены для причинной диагностики и проверки совместимости. API latency и распределение latency по корпусу имеют статус NOT RUN.
