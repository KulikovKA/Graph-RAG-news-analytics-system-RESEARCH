# Shared Concepts V2 · подготовка исследования гиперпараметров

Поэтапный скрипт готов к запуску на Corpus100. Проверены три процесса, повторное использование общей EE-выборки, возобновление после прерывания и автоматическое построение отчёта. На замороженном корпусе выполнен только smoke-run. [Результаты проверки](SMOKE.json)

## Вход и порядок CC

Вход — замороженный Corpus100 после существующего ER, 4 506 канонических сущностей. Используются сохранённые E5-small-v2 векторы имени и S1-контекста из Stage 3A.5.12. Модель и токенизатор зафиксированы ревизией `ffb93f3bd4047442299a41ebb6fa998a38507c52`, размерность каждого канала 384. EE применяет пороги 0,94 и 0,86 через AND, затем существующие защиты `result_type`, `incompatible_types` и `conflicting_expansions`. На 10 042 851 междокументной паре воспроизведены 8 173 кандидата до защит и 5 655 после. Проверка по сохранённым оценкам Stage 3A.5.13 подтвердила точное совпадение множества из 5 655 пар. [Предыдущая EE-регрессия](../shared_concepts_v2/REPORT.md) · [Stage 3A.5.13](../benchmark_3a5_13/ANALYSIS.md)

Ключ очереди CC сравнивает точную дробь Жаккара по убыванию и затем лексикографически сравнивает два канонических кортежа ID участников. Участники каждого концепта и два кортежа в паре упорядочены по возрастанию. Concept ID и версии используются для проверки актуальности записей и сохранения lineage. Политика генерации concept ID сохранена, включая сортировку родительских ID и версий в merge ID. Один и тот же допустимый набор кандидатов получает один порядок при любом namespace, run ID, label или хеше конфигурации. Это уточняет tie-break прежней реализации. Опубликованные метрики предыдущего dry-run относятся к его собственному порядку CC.

## Сетка и критерии отбора

Все границы включительны, шаг 0,01. Точки хранятся в целых сотых, δ передаётся в EC точной дробью.

| Этап | Какие точки рассчитываются |
|---|---|
| A | EC Name 0,90–1,00 × EC Context 0,85–0,95. Всего 121 точка при CC Name/Context 0,98/0,95 и δ 0,10. |
| B | Для трёх лучших разных пар EC из A сканируются CC Name 0,92–1,00 × CC Context 0,90–1,00, по 99 точек на пару EC. δ остаётся 0,10. |
| C | Для пяти лучших разных сочетаний EC/CC из B сканируется δ от 0,05 до 0,15, по 11 точек на сочетание. |
| D | Для пяти лучших точек C с различными EC/CC добавляются соседние точки на один шаг ±0,01 по одному параметру за раз. Учитываются границы всех пяти осей. Центры и уже вычисленные соседи переиспользуются. |

В каждом отборе применяется один и тот же лексикографический ключ. Сначала по убыванию идут охват дисциплин, охват документов, минимальная доля покрытых сущностей среди дисциплин и общий охват сущностей. Затем по возрастанию идут среднее число memberships на покрытую сущность, число концептов и кортеж пяти параметров. Доли для ранжирования сравниваются как точные дроби. Последний критерий разрешает все ничьи. После D отчёт показывает пять измеренных конфигураций с различными EC/CC по этому порядку. Базовая точка EC 0,95/0,92, CC 0,98/0,95 и δ 0,10 сохраняется независимо от рейтинга.

Критерии отбирают конфигурации для последующей проверки на разметке. Структурный охват и число memberships сами по себе не измеряют precision, recall или F1. Итоговые пороги требуют отдельного решения.

## Параллелизм, восстановление и результаты

Родитель проверяет вход и открывает единый EE-кэш с ключом от данных, рецепта, порогов, защит и кода EE. При отсутствии кэша он вычисляет EE один раз. Процессы получают готовые векторы и рёбра при инициализации, с локальной копией данных на Windows. Модель внутри воркеров не запускается. `--workers` по умолчанию равен 3, BLAS ограничен одним потоком на процесс. В терминале `tqdm` показывает общий и этапный прогресс, включая переиспользованные точки, и ETA. План следующего этапа зависит только от результатов предыдущего, отсортированных по заданным критериям.

Каждая точка имеет отдельный каталог и блокировку. Метрики сохраняются атомарно после точки. После подготовки очереди и каждые 500 CC merge-попыток по умолчанию сохраняется сжатый чекпойнт. При восстановлении завершённая точка читается из `metrics.json`, а незавершённая продолжает расчёт из своего чекпойнта при его наличии. Идентичность входа, расчёта и плана сверяется с манифестом. Смена числа воркеров доступна при восстановлении. Время и выборочный пик RSS записываются на конфигурацию, лимиты сессии и RSS одного процесса задаются через `--max-seconds` и `--max-rss-mib`.

Подробные сжатые каталоги удерживаются для базовой точки и текущего списка лучших разных EC/CC. У точки, выбывшей из списка, уже есть лучший результат с теми же EC/CC либо достаточно более сильных сочетаний. Добавление измерений не возвращает её в финальный список. Компактные метрики всех таких точек сохраняются. Подробные архивы финалистов содержат составы, две суммы, оценки, lineage, причины решений и раунды EC. Отдельно сохраняются исходные профили с evidence и 20 исторических диагностических случаев для каждого выбранного каталога.

| Артефакт | Содержание |
|---|---|
| `manifest.json`, `stage_A.json`–`stage_D.json` | Идентичность входа и кода, запланированные точки с учётом адаптивного отбора. |
| `trials/<точка>/metrics.json`, `results.json`, `results.csv` | Компактные метрики каждой точки, итоговая сводка с рейтингом и табличное представление. |
| `ec_heatmap.png`, `cc_heatmaps.png`, `delta.png` | Тепловые карты охвата сущностей по двум порогам и линии охвата/исключённых memberships по δ. |
| `REPORT.md`, `details/MANIFEST.json`, `complete.json` | Сравнение и список перспективных конфигураций, подробные экспорты и контрольные суммы завершённого прогона. |

JSON содержит число концептов и memberships, охват сущностей, документов и всех пяти дисциплин, уникальные пары документов и междокументные пары сущностей в одном концепте, размеры групп, число и долю парных концептов, распределение memberships по сущностям, строгие включения, исходы EC и CC и извлечённые из журнала причины отказа. Непосредственный отказ из-за вложенности учитывается отдельно от порогового отказа CC. При прошедшем EC и последующем отказе по вложенности EC учитывается как успешный, а merge как отклонённый. Исключённые memberships суммируются для принятых операций. Гистограммы с шагом 0,01 раздельно сохраняют name и context для EE-рёбер после защит, всех раундов EC, итоговых memberships и пороговых сравнений CC невложенных версий.

## Запуск и восстановление в PowerShell

Команды выполняются из корня RESEARCH с Python 3.11. Используются локальные замороженные артефакты Stage 3A.5.11–3A.5.13 и установленные зависимости из `uv.lock`, включая `tqdm` из `relex` и `matplotlib` из `research`.

Для полного поэтапного исследования предназначена команда ниже. Она подготовлена для самостоятельного запуска. После `Ctrl+C` выполните тот же блок с тем же `--run-id`.

```powershell
$env:PYTHONUTF8 = '1'
uv run --no-sync python scripts/study_shared_concepts_v2.py --run-id corpus100-sc-v2-study --workers 3
```

Результаты появятся в `artifacts/shared_concepts_v2/studies/corpus100-sc-v2-study/`. Для новой независимой проверки используется другой `--run-id`. Команда выполненного малого прогона и его восстановления приведена ниже.

```powershell
$env:PYTHONUTF8 = '1'
uv run --no-sync python scripts/study_shared_concepts_v2.py --run-id corpus100-v2-study-verified --smoke
```

## Пройденные проверки

- **81 целевой тест.** Регрессия воспроизводит сценарий, в котором прежний tie-break менял финальные множества. Новый порядок сохраняет состав при смене namespace, label и хеша конфигурации. Синтетический эксперимент сравнил результаты при одном и трёх процессах после принудительного прерывания координатора.
- **Smoke Corpus100.** Финальный прогон вычислил 9 уникальных конфигураций на всех этапах A–D, включая две новые точки D. Во время прерывания были живы три worker-процесса. После повторного запуска готовая точка сохранила прежний SHA-256, ещё две восстановились из чекпойнтов. Последующий запуск переиспользовал результаты завершённого прогона. Для семи общих точек двух smoke-запусков с разными run ID совпали полные структурные метрики и контрольные суммы множеств участников.
- **Артефакты.** Проверены CSV, JSON, все три PNG, контрольные суммы и полные каталоги базовой точки и двух smoke-финалистов. Выборочный максимальный RSS воркера в финальном smoke-run составил 288,9 МиБ. Smoke проверяет исполнение и воспроизводимость, а оценки качества требуют отдельной разметки.
